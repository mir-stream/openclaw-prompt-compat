# OpenClaw 2026.7.2 지문 파손 조사와 앵커 개선안

작성: 2026-07-27
상태: **§6.2 앵커 교체안을 `0.3.0`에 구현 반영 완료(§10). 빌더 함수를 직접 import한 실제 렌더
출력으로 독립 검증까지 마쳤다(§10.4). 게이트웨이 기동 캡처와 `2026.7.2` GA tarball 재실행은
미수행으로 남는다**
조사 대상: OpenClaw `2026.7.2-beta.4` (npm `beta` tag)
비교 기준: OpenClaw `2026.7.1` (현 npm `latest`는 `2026.7.1-2`)
선행 문서: [`2026-07-23-openclaw-prompt-compat-layer.md`](./2026-07-23-openclaw-prompt-compat-layer.md)

## 0. 요약

- `2026.7.2-beta`에서 현재 지문의 6개 앵커 중 **1개만** 깨졌다. Tooling 섹션 프리앰블 문장이다.
  나머지 5개는 문자 단위로 동일하다.
- 원인은 개별 수정이 아니라 `2026.7.2`의 **시스템 프롬프트 산문 일괄 축약**이다. CHANGELOG에 해당
  항목이 없다.
- 릴리스 11개를 실측한 결과 산문 리터럴의 전 버전 생존율은 1.0%, 헤딩·마커는 39.2%였다. 현재 지문은
  6개 앵커 중 유일한 산문 앵커에서 깨졌다.
- 그 산문 앵커를 빼고 `## Safety`·`## Workspace` 두 개의 구조 앵커로 대체하는 안을 제안한다. 앵커
  수가 늘어 변별력은 오히려 올라가고, 새 앵커는 모두 11/11 생존이다.
- 현재 `latest`(`2026.7.1-2`)는 영향이 없다. 그럼에도 이 제안은 `2026.7.2` GA를 기다리지 않고
  `0.3.0`에 반영했다. 이번 변경의 목적이 7.2 대응이 아니라 지문 수명 연장이기 때문이다(§10).

## 1. 무엇이 깨졌는가

바뀐 것은 다음 한 줄이다.

```text
2026.7.1        Available tools are policy-filtered. Names are case-sensitive; call exactly as listed.
2026.7.2-beta   Tools policy-filtered. Names case-sensitive; call exact.
```

`src/index.ts`의 `TOOLING_SECTION_PREAMBLE_PATTERN`이 이 문장을 리터럴로 요구하므로 지문 전체가
match에 실패한다. 재구성한 프롬프트로 실측한 결과는 다음과 같다.

```text
2026.7.1         => replaced: true   | You are a personal assistant running within OpenClaw.
2026.7.2-beta.4  => replaced: false  | You are a personal assistant running inside OpenClaw.
```

프롬프트 빌더 파일 경로도 함께 바뀌었다. `dist/system-prompt-config-*.js` →
`dist/system-prompt-params-*.js`. 파일명은 지문과 무관하지만 조사·재현 시 위치가 달라진다.

## 2. 앵커별 판정

| # | 앵커 | `2026.7.2-beta.4` |
| --- | --- | --- |
| ① | `You are a personal assistant running inside OpenClaw.` (문자열 절대 시작) | 동일 |
| ② | `\n## Tooling\n` | 동일 |
| ③ | 고정 Tooling preamble | **변경** |
| ④ | `## Workspace Files (injected)` | 동일 |
| ⑤ | `<!-- OPENCLAW_CACHE_BOUNDARY -->` | 동일 (`@openclaw/ai`에서 정의, 값 불변) |
| ⑥ | `## Runtime` | 동일, 캐시 경계 뒤 순서도 유지 |

프롬프트 조립 방식(`lines.filter(Boolean).join("\n")`)도 동일하다. 빈 문자열 원소가 제거되므로
identity 문장과 `## Tooling`이 인접한다는 전제는 그대로 유효하다.

## 3. 원인 — `2026.7.2`의 프롬프트 일괄 축약

앵커 ③만 겨냥한 수정이 아니다. 시스템 프롬프트의 산문 전반이 토큰 절감 목적으로 축약됐다.

| 위치 | `2026.7.1` | `2026.7.2-beta.4` |
| --- | --- | --- |
| Tooling preamble | `Available tools are policy-filtered. Names are case-sensitive; call exactly as listed.` | `Tools policy-filtered. Names case-sensitive; call exact.` |
| TOOLS.md 안내 | `TOOLS.md is usage guidance, not availability.` | `TOOLS.md guides usage; never grants availability.` |
| Workspace 경로 | `Your working directory is: …` | `Working directory: …` |
| Workspace Files 본문 | `These user-editable files are loaded by OpenClaw and included below in Project Context.` | `User-editable; OpenClaw loads below as Project Context.` |
| `## Silent Replies` | 12줄 | 3줄 |
| `## OpenClaw Self-Update` | 섹션 존재 | 섹션 삭제 |
| `## OpenClaw Control` | 고정 3줄 | `hasOpenClaw` 분기로 재구성 |

반면 헤딩과 마커는 전부 그대로다. `## Tooling`, `## Workspace Files (injected)`,
`<!-- OPENCLAW_CACHE_BOUNDARY -->`, `## Runtime` 모두 변경 없다. **헤딩·마커는 전수 생존, 순수
산문은 전수 변경**이라는 경계가 명확하다.

`2026.7.2` CHANGELOG에는 이 축약에 대응하는 항목이 없다. 릴리스 노트만으로는 감지할 수 없다.

축약 문구는 `2026.7.2-beta.1`부터 이미 적용돼 있었고 `beta.4`까지 동일하다. beta 구간 중 재변경은
없었다.

## 4. 현재 영향 범위

- 현 npm `latest`인 `2026.7.1-2`는 구 문구를 유지한다. **운영 중인 설치본은 정상 동작한다.**
- `2026.7.2`에서는 치환이 일어나지 않을 뿐 프롬프트가 손상되지 않는다. 설계된 fail-closed 동작이다.
- 다만 manifest의 `openclaw.compat.pluginApi`가 `>=2026.7.1`이므로 `2026.7.2`에서도 설치·load는
  성공하고 **경고 없이 무동작**한다. GA 대응 시 함께 검토할 항목이다(6.3 참조).

## 5. 릴리스 이력 실측 — 무엇이 패치되는가

앵커 후보를 감으로 고르지 않기 위해, 실제 릴리스 이력에서 프롬프트 리터럴의 생존율을 측정했다.

### 5.1 방법

`2026.2.26`부터 `2026.7.2-beta.4`까지 약 5개월에 걸쳐 stable 11개 릴리스를 샘플링했다. 각 tarball의
`dist/`에서 identity 문장과 `## Tooling`을 함께 포함한 파일을 프롬프트 빌더로 식별하고, 그 파일의
double-quoted 문자열 리터럴을 추출해 버전 간 존재 여부를 대조했다.

샘플: `2026.2.26` `2026.3.24` `2026.4.15` `2026.4.29` `2026.5.12` `2026.5.28` `2026.6.5` `2026.6.11`
`2026.6.33` `2026.7.1` `2026.7.2-beta.4`

빌더 파일명은 기간 중 세 번 바뀌었다. `pi-embedded-*.js` → `system-prompt-*.js` →
`system-prompt-config-*.js` → `system-prompt-params-*.js`.

### 5.2 산문 대 헤딩

```text
                    고유 개수    11/11 전 버전 생존
산문(설명 문장)       2,112개         22개  ( 1.0%)
헤딩·마커                51개         20개  (39.2%)
```

산문 2,112줄 중 1,394줄(66%)은 단 한 버전에서만 존재했다. 대부분의 설명 문장은 한두 릴리스 안에
사라진다.

11개 버전을 모두 통과한 산문 22줄도 앵커로는 쓸 수 없다. 대부분 `- ls: list directory contents`
같은 툴 목록 설명이라 툴 가용성에 따라 렌더 여부가 갈리고, 나머지는 `Host browser control: allowed.`
같은 조건부 한 줄이다. 프롬프트 골격에서 무조건 렌더되는 산문은 **identity 문장 하나뿐**이다.

### 5.3 현재 앵커 6개의 이력

```text
                                            2.26 3.24 4.15 4.29 5.12 5.28 6.5 6.11 6.33 7.1 7.2β
① identity 문장                               ●    ●    ●    ●    ●    ●    ●    ●    ●   ●   ●   11/11
② ## Tooling                                  ●    ●    ●    ●    ●    ●    ●    ●    ●   ●   ●   11/11
③ Available tools are policy-filtered…        ·    ·    ·    ·    ●    ●    ●    ●    ●   ●   ·    6/11
④ ## Workspace Files (injected)               ●    ●    ●    ●    ●    ●    ●    ●    ●   ●   ●   11/11
⑤ <!-- OPENCLAW_CACHE_BOUNDARY -->            ·    ·    ●    ●    ●    ●    ●    ●    ●   ●   ●    9/11
⑥ ## Runtime                                  ●    ●    ●    ●    ●    ●    ●    ●    ●   ●   ●   11/11
```

앵커 ③은 6개 중 **가장 늦게 등장해 가장 먼저 소멸했다.** `2026.5.12`에 도입돼 `2026.7.2`에서
사라졌고 수명은 6개 릴리스였다. 지문 채택 시점(`2026.7.1`)에는 이미 존재했으므로 안정성 이력을
확인할 근거가 없는 상태에서 고른 앵커였다.

앵커 ⑤ 캐시 경계는 `2026.4.15`에 도입된 뒤 문자열이 한 번도 바뀌지 않았다. `2026.7.1`부터 정의
위치만 `@openclaw/ai`로 이동했고 값은 동일하다.

### 5.4 렌더 순서

```text
2026.2.26   identity → ## Tooling → ## Safety → ## Workspace → ## WsFiles →           → ## Runtime
2026.3.24   identity → ## Tooling → ## Safety → ## Workspace → ## WsFiles →           → ## Runtime
2026.4.15   identity → ## Tooling → ## Safety → ## Workspace → ## WsFiles → cacheBound → ## Runtime
     ⋮        (4.29 · 5.12 · 5.28 · 6.5 · 6.11 · 6.33 · 7.1 동일)
2026.7.2β   identity → ## Tooling → ## Safety → ## Workspace → ## WsFiles → cacheBound → ## Runtime
```

5개월 동안 순서가 바뀌지 않았다. 캐시 경계만 `2026.4.15`에 중간 삽입됐고 이후 고정이다.

## 6. 앵커 개선 추천안

### 6.1 후보 심사

11/11 생존 헤딩 20개 중 **무조건 렌더**되고 순서가 고정된 것만 남겼다.

| 후보 | 생존 | 렌더 조건 | 판정 |
| --- | --- | --- | --- |
| `## Tooling` | 11/11 | 무조건 | 채택 (기존 유지) |
| `## Safety` | 11/11 | 무조건 (`safetySection` 상수 배열) | **신규 채택** |
| `## Workspace` | 11/11 | 무조건 | **신규 채택** |
| `## Workspace Files (injected)` | 11/11 | 무조건 | 채택 (기존 유지) |
| `<!-- OPENCLAW_CACHE_BOUNDARY -->` | 9/11 | 무조건 (`2026.4.15`~) | 채택 (기존 유지) |
| `## Runtime` | 11/11 | 무조건 (마지막 `lines.push`) | 채택 (기존 유지) |
| `## Tool Call Style` | 11/11 | `buildOverridablePromptSection`으로 감싸짐. provider override 시 소멸 | 탈락 |
| `## Messaging` | 11/11 | `isMinimal`·채널 의존 | 탈락 |
| `## Sandbox` | 11/11 | `sandboxInfo.enabled` 의존 | 탈락 |
| `## Model Aliases` | 11/11 | `modelAliasLines` 의존 | 탈락 |
| `## Reactions` | 11/11 | `reactionGuidance` 의존 | 탈락 |
| `## Voice (TTS)` | 11/11 | `ttsHint` 의존 | 탈락 |

`## Tool Call Style`은 11/11 생존이지만 provider가 해당 섹션을 override하면 헤딩째로 사라진다.
생존율만 보고 고르면 안 되는 대표 사례다. `## Messaging`·`## Voice (TTS)`는 각 builder 함수 첫
줄이 `if (params.isMinimal) return []`이라 subagent 프롬프트에서 통째로 빠진다.

신규 채택 두 개는 `promptMode: "minimal"`에서도 렌더된다. 11개 버전 전부에서 `safetySection`
상수에 `isMinimal`·`promptMode` 분기가 없고 `...safetySection`이 조건 없는 spread이며,
`"## Workspace"`도 조건 없는 배열 원소다. 따라서 main·subagent 양쪽 프롬프트를 모두 덮는다.

**사후 보강(§10.4 독립 검증에서 확인).** `## Tool Call Style` 탈락 근거는 위에 쓴 wrapper 사용
여부보다 강하다. 결정적인 것은 provider가 override할 수 있는 섹션 id가 닫힌 3원소 타입이라는
점이다.

```ts
ProviderSystemPromptSectionId = "interaction_style" | "tool_call_style" | "execution_bias"
```

이 타입은 `2026.5.12`~`2026.7.2-beta.4`에서 동일하고 호출 지점 4개도 `2026.7.1`·`2026.7.2-beta.4`가
같다. `safety`·`workspace`는 override 대상으로 **표현 자체가 불가능**하다. 즉 이 표가 경고한
"생존율만 보고 고르면 안 되는 함정"은 신규 채택 두 앵커에 대해 구조적으로 닫혀 있다. 판정은
바뀌지 않고 근거만 강해졌다.

### 6.2 제안 지문

산문 앵커 1개를 구조 앵커 2개로 교체한다.

```ts
const identityPattern =
  "You are a personal assistant running inside OpenClaw\\.";
const marker = (s: string) => `(?=([\\s\\S]*?(?<![^\\n])${s}\\n))`;

new RegExp(
  `^${identityPattern}(?=` +
    "\\n## Tooling\\n" +
    marker("## Safety") + "\\1" +
    marker("## Workspace") + "\\2" +
    marker("## Workspace Files \\(injected\\)") + "\\3" +
    marker("<!-- OPENCLAW_CACHE_BOUNDARY -->") + "\\4" +
    marker("## Runtime") + "\\5" +
    ")",
);
```

기존 구조는 그대로 유지한다. 전체가 lookahead 안에 있으므로 match span은 identity 문장 하나이고,
각 marker 구간은 atomic lookahead capture + backreference로 확정 소비해 backtracking이 선형으로
유지된다.

```text
현재                                    제안
─────────────────────────────────      ─────────────────────────────────
① identity          11/11              ① identity          11/11
② ## Tooling        11/11              ② ## Tooling        11/11
③ 프리앰블 산문       6/11  ← 취약       ③ ## Safety         11/11  ← 신규
④ ## WsFiles        11/11              ④ ## Workspace      11/11  ← 신규
⑤ 캐시 경계           9/11              ⑤ ## WsFiles        11/11
⑥ ## Runtime        11/11              ⑥ 캐시 경계           9/11
                                       ⑦ ## Runtime        11/11
```

`## Workspace`는 `## Workspace Files (injected)`의 접두사지만, marker 패턴이 끝에 `\n`을 요구하므로
후자에 잘못 걸리지 않는다. 또한 렌더 순서상 `## Workspace`가 먼저 나오므로 lazy 탐색이 올바른
위치에서 멈춘다.

### 6.3 함께 검토할 항목

지문과 별개로, `2026.7.2` 대응 시 다음을 같이 판단한다.

- `openclaw.compat.pluginApi`와 `install.minHostVersion`의 상한 선언 여부. 현재는 상한이 없어
  프롬프트 구조가 바뀐 host에서도 설치·load에 성공하고 조용히 무동작한다.
  → 결론: 상한을 두지 않는다(§10.2).
- 지문 불일치 시 경고 로그를 남길지 여부. 현재는 무동작이 관측되지 않는다. 다만
  `registerTextTransforms`는 등록 시점 API이고 match 실패는 런타임 문자열마다 발생하므로, 경고를
  남기려면 등록 시점이 아닌 별도 경로가 필요하다.
  → 결론: `0.3.0`에서는 구현하지 않고 후속 과제로 남긴다(§10.2, §10.3).

## 7. GA 시 남은 검증

§1~§6의 판정은 빌더 소스에서 **재구성한 프롬프트** 기준이다. 이후 §10.4의 독립 검증이 각 버전을
설치해 **빌더 함수를 직접 import한 실제 렌더 출력**까지 확인했다. 게이트웨이를 기동해 뽑은 캡처는
아직 없다. 체크된 항목은 `0.3.0` 구현(§10) 과정에서 완료했고, 나머지는 GA 이후에 수행한다.

- [ ] `2026.7.2` GA tarball에서 5.3·5.4를 재실행해 앵커·순서가 beta와 동일한지 확인한다. — GA
      미출시. `beta.4` 기준 판정만 있다.
- [ ] `2026.7.1`과 `2026.7.2` 양쪽에서 실제 outbound system prompt를 캡처해 제안 지문이 match하는지
      확인한다. `0.2.0` acceptance와 같은 mock outbound 방식을 재사용한다. — **부분 완료.** 빌더
      함수를 직접 import한 실제 렌더 출력까지는 확인했다(§10.4). 남은 것은 게이트웨이를 기동해
      outbound 경로에서 캡처하는 단계뿐이다.
- [x] `promptMode: "minimal"`(subagent) 렌더에서 `## Safety`·`## Workspace`가 실제로 포함되는지
      확인한다. — 실측으로 확정했다. `2026.7.2-beta.4` minimal 렌더 44번째 줄에 `## Safety`가
      존재하고, `2026.7.1`·`2026.7.2-beta.4` 양쪽 minimal 렌더에서 `## Safety`·`## Workspace`가
      모두 확인됐다(§10.4).
- [x] `test/index.test.js`의 `minimalPrompt()` 픽스처에 `## Safety`를 추가한다. — 추가했다.

## 8. 재현 방법

```sh
# 버전별 tarball 확보 (dist만 추출)
for V in 2026.2.26 2026.3.24 2026.4.15 2026.4.29 2026.5.12 2026.5.28 \
         2026.6.5 2026.6.11 2026.6.33 2026.7.1 2026.7.2-beta.4; do
  mkdir -p "v$V" && (cd "v$V" \
    && npm pack "openclaw@$V" >/dev/null 2>&1 \
    && tar xzf "openclaw-$V.tgz" package/dist \
    && rm -f "openclaw-$V.tgz")
done

# 프롬프트 빌더 파일 식별
grep -rl "personal assistant running inside OpenClaw" v2026.7.2-beta.4/package/dist/

# 앵커 문구 대조
for V in v2026.*; do
  printf '%-18s ' "$V"
  grep -rho "Available tools are policy-filtered[^\"]*\|Tools policy-filtered[^\"]*" \
    "$V/package/dist/" | sort -u | head -1
done
```

전 버전 리터럴 생존율(5.2)과 렌더 순서(5.4)는 빌더 파일에서 double-quoted 리터럴을 추출해 집합
연산으로 산출했다. 렌더 순서는 배열 원소 위치가 아니라 실제 spread·push 지점을 기준으로 측정해야
한다. `safetySection`처럼 상수로 먼저 선언되고 나중에 spread되는 섹션이 있어 선언 위치와 렌더
위치가 다르다.

### 8.1 재현 시 빠지기 쉬운 함정 두 가지

**캐시 경계를 openclaw dist에서 grep하면 0건이다.** `2026.7.1`·`2026.7.2-beta.4` 어느 쪽에서도
`OPENCLAW_CACHE_BOUNDARY`가 잡히지 않는다. 상수 정의가 `@openclaw/ai`로 이동했기 때문이다(§2 ⑤).
위 레시피를 그대로 돌린 사람은 이를 "앵커 소멸"로 오독하기 쉽다. 실제 렌더 출력에는 경계가 정상
출력된다. 앵커 존재 여부는 grep이 아니라 렌더 결과로 판단해야 한다.

**`2026.2.26`·`2026.3.24`는 빌더를 import하면 안 된다.** 이 두 버전은 프롬프트 빌더가 monolithic
CLI 번들 안에 있어 import만으로 부트스트랩 부작용이 실행된다. `~/.openclaw/openclaw.json`을 읽고,
config 검증 오류를 출력하고, auth-profiles sync와 telegram·model-catalog 초기화를 돌린 뒤 throw
한다. **실제 사용자 환경을 건드린다.** 이 두 버전은 import 대신 소스 분석으로 처리한다.

## 10. 구현 반영 (0.3.0)

6.2 제안을 그대로 `0.3.0`에 반영했다. `2026.7.2` GA를 기다리지 않았다. 이번 변경의 목적은 7.2 대응이
아니라 지문의 수명을 늘리는 것이고, 그 근거(5.2의 산문 1.0% 대 헤딩 39.2%)는 GA 여부와 무관하게
이미 확정된 측정치다.

### 10.1 변경 내용

지문에서 산문 앵커를 제거하고 구조 앵커 2개를 넣었다. 최종 정규식은 다음과 같다.

```text
^You are a personal assistant running inside OpenClaw\.(?=
  \n## Tooling\n
  (?=([\s\S]*?(?<![^\n])## Safety\n))\1
  (?=([\s\S]*?(?<![^\n])## Workspace\n))\2
  (?=([\s\S]*?(?<![^\n])## Workspace Files \(injected\)\n))\3
  (?=([\s\S]*?(?<![^\n])<!-- OPENCLAW_CACHE_BOUNDARY -->\n))\4
  (?=([\s\S]*?(?<![^\n])## Runtime\n))\5
)
```

전체가 lookahead 안이고, `^` 절대 시작 앵커, atomic lookahead capture + backreference, non-global·
non-sticky는 그대로다. match span은 여전히 identity 문장 하나다.

| 파일 | 변경 |
| --- | --- |
| `src/index.ts` | `TOOLING_SECTION_PREAMBLE` export와 내부 `TOOLING_SECTION_PREAMBLE_PATTERN` 삭제. `SAFETY_SECTION_MARKER`·`WORKSPACE_SECTION_MARKER` export 추가. marker 상수 선언 순서를 5.4의 실제 렌더 순서에 맞춤 |
| `test/index.test.js` | 픽스처를 `2026.7.1`·`2026.7.2-beta` 두 형태로 분리. 프리앰블은 지문에서 빠졌으므로 픽스처 내부 리터럴로 격하 |
| `openclaw.plugin.json`, `package.json` | `0.2.0` → `0.3.0` |
| `README.md` | 지문 목록을 7단계 구조 앵커로 갱신 |

`TOOLING_SECTION_PREAMBLE`은 더 이상 지문에 쓰이지 않으므로 export를 남기지 않았다. 지문 요소가
아닌 상수를 export로 남기면 오해를 부른다. 0.x 패키지이므로 제거가 허용된다.

캡처 그룹이 3개에서 5개로 늘었다. `escapeReplacementSentence`가 `$`를 `$$`로 escape하므로 `$1`-`$9`
치환 시퀀스 처리는 그대로 유효하고, 해당 JSDoc의 개수 표기를 함께 고쳤다.

### 10.2 확정한 결정 3건

- **manifest 상한을 두지 않는다.** `openclaw.compat.pluginApi`·`install.minHostVersion`·
  `peerDependencies.openclaw`는 `>=2026.7.1`을 유지한다. 상한은 프롬프트 구조가 유지된 host에서도
  설치를 막는다. 새 지문은 구조 앵커만 쓰므로 산문 축약 같은 변경에는 영향을 받지 않고, 구조가
  실제로 바뀌면 fail-closed로 무동작한다. 상한이 막아줄 실패는 이미 무해하고, 상한이 만들 실패는
  무해하지 않다.
- **지문 불일치 경고는 이번 릴리스에 넣지 않는다.** `registerTextTransforms`는 등록 시점 API이고
  match 실패는 런타임 문자열마다 발생한다(6.3). 문자열마다 경고하면 정상 입력에서도 대량 발생하므로
  등록 시점이 아닌 별도 관측 경로 설계가 필요하다. 앵커 교체와 묶을 변경이 아니다.
- **`openclaw.build.openclawVersion`·`pluginSdkVersion`은 `2026.7.1`을 유지한다.** SDK 의존이
  바뀌지 않았다. 이번 변경은 정규식 상수 하나다.

### 10.3 남은 과제

- `2026.7.2` GA tarball로 5.3·5.4 재실행. GA가 아직 없다.
- 게이트웨이를 기동해 outbound 경로에서 실제 시스템 프롬프트를 캡처하는 검증(§7). 빌더 함수 직접
  import 렌더까지는 §10.4에서 확인했으므로, 남은 것은 이 한 단계다.
- 지문 불일치 관측 경로. 지금은 host 프롬프트가 바뀌어도 무동작이 조용히 진행된다. 이 상태가
  `0.3.0`에서도 유지된다.
- `setup_openclaw`의 기본 OpenClaw 버전과 `--prompt-compat-version` 기본값 갱신. 이 저장소 밖이다.

### 10.4 독립 검증 결과

별도 검증자가 리포와 무관하게 수행했다. 방법은 §1~§6의 소스 재구성보다 강하다. 각 버전을 실제로
설치한 뒤 **프롬프트 빌더 함수를 직접 import해 렌더한 출력**을 입력으로 썼다. 다만 게이트웨이를
기동해 outbound 경로에서 뽑은 캡처는 아니다. 그 단계는 여전히 미수행이다(§10.3).

**실제 렌더 match.** `2026.7.1`·`2026.7.2-beta.4` × {default, minimal} 네 가지 실제 렌더가 모두
새 지문에 match했다. 현행(`0.2.0`) 지문은 `2026.7.2-beta.4` 양쪽을 reject했다 — §1의 파손이
재구성이 아니라 실제 렌더로 재현됐다. `promptMode: "none"` 렌더는 양쪽 버전 모두 reject다.

**설정 매트릭스.** 버전당 17개 설정 변형(sandbox, provider override 전 조합, modelAlias, bootstrap,
reasoningHint, tts, reactions, 툴 없음, 악성 marker 주입)에서 새 지문 32/32 match.

**하위 호환 범위가 뒤쪽으로도 넓어졌다.** 새 지문은 `2026.4.15`·`2026.4.29` 렌더에서도 match한다.
현행 지문은 이 두 버전을 reject한다 — 산문 프리앰블이 `2026.5.12` 도입이기 때문이다(5.3 앵커 ③).
즉 앵커 교체는 앞쪽(7.2)뿐 아니라 뒤쪽으로도 적용 범위를 넓혔다. 실측 하한은 `2026.4.15`이고,
그 이유는 캐시 경계 앵커가 그때 도입됐기 때문이다(5.3 앵커 ⑤, 9/11). 이건 지문이 match하는 범위일
뿐 지원 범위가 아니다. 지원 하한은 `>=2026.7.1` 그대로다.

**오탐 사냥 결과 없음.** 앵커 체인을 `contextFiles`·`workspaceNotes`·`extraSystemPrompt`·
`promptContribution.stablePrefix`·`workspaceDir` 전 주입 경로로 밀어 넣어도 치환은 정상이었다.
구조적 이유가 있다. 줄 시작 헤딩이 추가로 생기면 lazy 탐색이 더 앞에서 바인딩될 뿐이고, 치환
span은 identity 문장 하나로 고정돼 있다. 잘못 바인딩된 marker는 출력에 아무것도 쓰지 않는다.

**접두사 혼동과 fail-closed.** `## Safety`와 `## Workspace Files (injected)`만 있고 `## Workspace`가
없는 입력은 실측에서 reject됐다. 후행 공백, 대소문자 변경, 줄 중간 배치, CRLF도 전부 reject다.

**성능.** 실제 `2026.7.2-beta.4` 프롬프트(6KB) 0.0025ms. 전체 앵커 체인 20,000회 반복(430KB)
최악 0.143ms, 50,000회 반복(4.3MB) 0.311ms. 크기가 10배로 늘 때 11배 — 선형이다.

**정규식 동일성.** 리포에서 컴파일된 `OPENCLAW_SYSTEM_PROMPT_FINGERPRINT.source`가 §6.2 제안 및
검증자의 독립 재구현과 바이트 단위로 일치했다.
